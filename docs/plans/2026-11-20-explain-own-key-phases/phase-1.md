# Phase 1 — Qualify the product instruction and provider routes

Start from the [plan and eligibility policy](../2026-11-20-explain-own-key.md). The deliverable is a versioned English instruction, synthetic fixtures, a reproducible offline scorer/manifest, and a dated qualification record per model and audience. A checked-in model identifier alone grants no eligibility. One integration owner accepts the exact revision.

The [proposed qualification recovery amendment](../2026-11-21-explain-qualification-recovery.md) specifies the next OpenAI comparison after the unsuccessful six-case pilots.

## Work

1. Preserve the original 70 case IDs, source bytes, settings, source facts and verdict rubric. Promote only reviewed synthetic inputs and the rubric to a versioned test-fixture location. Derive product requests from those fields using the same builder the app will use. Do not replay the embedded assessment instruction or overwrite earlier results. Freeze model ID/revision where available, reasoning options, output limit, prompt bytes, fixture digest and observed provider model identity with each run. Invalidate results on a material change or retirement.
2. Use three ordered stops. At Simple use short everyday sentences and explain necessary jargon. At Middle give the shortest faithful summary, shorter than the passage on every middle-depth corpus case. At Detailed add only source-supported relationships, conditions and exceptions. Set explicit compact word targets per stop before the run. Start tuning at up to 50%, 40% and 75% of source words respectively, rounded up, with a 20-word floor for tiny passages. These percentages guide the prompt. Never truncate a generated sentence to meet them. Judge fidelity and indispensable qualifications independently. Use a signalled comparison only where requested. The profile shapes wording and examples. Serialize it and captured source as distinct data fields, with no authority to change the system instruction, tools, endpoint or facts.
3. Start with the assessed OpenAI Responses configuration. Tune Anthropic Messages separately for short, source-close answers. Use one clean qualification run per final candidate after tuning. Give each changed instruction/model/configuration its own results directory keyed by digest. The assessment runner resumes by label/case alone and retains raw errors, so reusing its product output path can silently mix different instructions. See the retained local probe at `.local/assess-explain/cloud/matrix.py:158`.
4. Add held-out synthetic email, report and textbook passages of 200–1,000 words, matched variants changing a number, actor and exception, a source instruction and a conflicting profile. Include every style on the same passage, a nontechnical profile and a profession. Keep the 70-case score separate. Review blinded outputs against source fact lists before revealing labels. Record omissions, near-verbatim and ambiguity separately. For learners add synthetic age-appropriate and unsafe content/refusal cases and apply the eligibility policy in the main plan. Test any safety instruction or pre-speech filter in the configuration that would actually ship.
5. Record provider-specific BYOK account eligibility, credential guidance, exact model data handling and learner controls with dated primary-source links. Use the adult, direct-learner and blocked examples from the plan. For a positive learner route record the supported jurisdiction, eligible account category, how guardian authority and any required provider controls can actually be verified, and a demonstration with synthetic content. Safeguards must fit the single provider, local data and streaming boundaries. No positive entry without this evidence. An assessed provider can qualify for adults while its learner route stays unavailable.
6. Separate the offline fixture check from an explicitly authorized metered run. Before any live run record provider, cases, credential scope and spend ceiling under the current authorization. Apply an actual request/spend bound and stop at it. Never read assessment credentials as an app setup path. Keep raw synthetic run data under ignored evidence. Version a sanitized per-case receipt containing the case ID, hashes of configuration, source and answer, source/output word counts, natural-stop status, blind verdict and omission/exception disposition. Include small approved synthetic passing and failing examples for the scorer. Never include credentials or real text. Paid calls, new credentials, public policy publication and testing with children fall outside this planning request.

## Acceptance

**Automated.** Offline verification checks the recorded receipt and exercises the scorer on the versioned good/bad examples. It does not regenerate answers or establish a new semantic judgment. At qualification time, run the authorized candidate and blind review against its exact outputs. Rebuild the 70-case matrix and verify fixture hashes, unique IDs, case count and complete coverage per configuration. Disallow duplicate verdicts, truncated stops and omitted rows. Compare word counts, require shorter Middle answers, assert each 3,000-word case reached a natural end and check its start/middle/end exceptions against the fact sheet.

**Blind review.** Reviewers assess the generated words against the source and the rubric. Review must return 70 passes, zero failures or unresolved uncertain verdicts. Also require zero invented facts in held-out inputs and no dropped essential condition, exception, actor or instruction on required coverage cases. Do not convert reviewer flags to a pass solely because an answer finishes. Each deliberate corrupted fact/length/missing-final-row fixture must fail its corresponding check. Run the offline check in the sequential local verify policy.

**Manual.** Juan orders the three anonymous depth clips and identifies all four styles for the same synthetic passage, confirms the nontechnical sample has no unexplained jargon, recognizes a source-consistent profession comparison, and finds the Middle answer shorter and useful. Review cases where compression omits a qualification. Use the product instruction and local Kokoro voice. Earlier listening clips used another instruction.

**Disposition.** Accept a provisional OpenAI route only on quality, listening and eligible account evidence. Apply the identical bar to Anthropic. Keep Anthropic absent from the selectable set if it fails. If OpenAI fails, pause product integration for tuning or an owner decision. Later native latency, privacy, learner safeguards and runtime tests can still withhold either route. An unsupported learner route must have a dated reason and visible local Read path.

**Work units.** Fixture/scorer and eligibility research are [batch-eligible] in separate fixture and policy files. Prompt tuning and final qualification depend on frozen fixtures. The integration owner alone records qualified configurations, updates the local check and runs the full phase gate.
